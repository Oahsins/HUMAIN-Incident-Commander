# Decisions and trade-offs

Dated log of design decisions. Times are Riyadh (UTC+3). Codex records its hashes in `baselines/FROZEN.json` and `scenarios/heldout/SEALED.json`; Claude copies them here.

| Date | Decision | Why / consequence |
|---|---|---|
| 2026-10-29 | Challenge 1, idea C1-H1: the ABCDE incident commander | Our strongest idea after comparing the options, and Codex's independent comparison agreed; the design borrows the emergency-medicine method Omar brought to it (primary survey, triage, SBAR). |
| 2026-10-29 | Banking is the main test system and carries the sealed exam; a second system is the transfer test; the lead story is chosen at Fri 14:00 | Banking gives an exact recovery check (the ledger must balance, every payment posts once). The transfer test shows the same frozen agent works on a system it was never tuned on. |
| 2026-10-29 | The agent is system-agnostic: a 5-function adapter is all it needs; a test system adds a control layer and a checker | Omar's requirement: it must plug into any system, including one the organisers supply. |
| 2026-10-29 | The agent's author never writes the exam | Claude builds the agent and the practice faults; Codex writes the held-out and blind faults, the sealed exam and the scripted runbook baseline. Removes the "tested on its own faults" objection. |
| 2026-10-29 | Two Codex sessions on the laptop | Session A writes and holds the sealed exam and runs no agent arm before seal 2; Session B builds the runbook and the harness, runs the pilot, and never sees the sealed files. |
| 2026-10-29 | The exam is sealed twice, and the push time is the evidence | Seal 1 (scenarios, by 03:00 Fri, 05:00 at the latest) and seal 2 (plugin code, by Fri 14:00). The time GitHub received each push proves when the exam was fixed; commit times are set by the committer. The core40 and robust20 lists are pre-registered in `SEALED.json`. |
| 2026-10-29 | The dispatch system is built after `freeze-1`, by Claude; its faults and incidents by Codex | The frozen hashes then show the agent never saw the second system, and its author never sees the transfer exam before the run. A 10-incident transfer run is never cut. |
| 2026-10-29 | The runbook freezes with the agent at `freeze-1` | Both get the same tuning window, which is fairest. After the tag, only an exception fix, with a new hash and a `FROZEN.json` line. |
| 2026-10-29 | Provider errors and harness timeouts are not agent failures | `api_error` and `harness_timeout` cases are re-run once at the end and reported separately (CONTRACT section 11). |
| 2026-10-29 | The model robustness condition is `model_swap` (renamed from the cheaper-model condition) | The robustness question is whether the frozen agent works on a model it was not tuned on, not whether it is cheap. |
| 2026-10-29 | Contract version 1.1: the bank profile and the review fixes | After 1.1, sections 3, 5, 7, 8 and 9 change only by adding optional fields with defaults until `freeze-1`. `CONTRACT_VERSION` in `ic/contract.py` stays 1 until something is published. |
| 2026-10-29 | Deck-review trims adopted | No ECC-style record; English-only SBAR; "weighted shortest-job-first", not START; Smith's rule dropped as evidence; the first-come-first-served ablation is kept because it was cheap to build; deck cut to 10 slides. |
| 2026-10-29 | 30 practice scenarios, written by `scenarios/dev/make_dev.py`: dev-01 to dev-20 for tuning, dev-21 to dev-30 for the pilot only | The agent and the runbook tune on the same 20 cases, and the pilot uses 10 that neither was tuned on. Each case has 1 to 3 harmless background changes from its own seed. Every case was run on a live copy with its labelled fixes before the push. |
| 2026-10-29 | Contract 1.1 completed before Codex started: fixes may carry `then` actions, and runtime values come from the manifest | A poison item is quarantined and then the crashed worker restarted, both in the label. A runtime value such as a queue item id is `null` in the label and filled from the fault's manifest `detail`, so the sealed labels and the oracle agree without either side seeing the other (CONTRACT section 8). |
| 2026-10-29 | Robustness cases come from core40 and name their source | `robust20` is drawn from `core40`, so a cut to core40 keeps every pair. Each `robustness.jsonl` line has the id of its robust20 case plus `-ff` or `-xs` and a `source_id`, and the new four-fault and extra-service cases are checked by `noop` and `oracle` like the exam (220 robustness runs instead of 140). |
| 2026-10-29 | Neutral sealed names and a live check before seal 1 | `SEALED.json` commits file paths and case ids before `freeze-1`, so only the three named types keep their names and case ids are `h-01` to `h-60`. Session A checks every sealed type and variant live before seal 1, because labels can never change after it, and the oracle is re-run once on every fault case where it was red, as the validity rule needs. |
| 2026-10-29 | Codex commits under its own name | Each Codex session sets a repository-local git identity, "Codex (Session A)" or "Codex (Session B)", with Omar's GitHub no-reply address, and ends every commit message with "Made by Codex (Session A)" or "(Session B)". The history shows who made what, and no private address is published. |
| 2026-10-29 | Standard-library services plus psutil, no Docker, no web framework | Fewer moving parts on Windows; each service is a small Python web server Omar can read. |
| 2026-10-29 | Work started on 29 Oct, before the event | Disclosed here and in the README; the commit history shows the dates. The basis is in Omar's private notes. |
| 2026-10-30 | `extra_service` adds a notifications worker | Kind `worker`, depends on the ledger, impact weight 0.1, actions restart, rollback, revert_config and quarantine, settings `batch_size` 50 and `poll_interval_s` 0.2, port offset 8. A ledger trigger queues one receipt per posted payment in the same transaction, so payments' code and the default bank do not change. The checker gains one rule, under `extra_service` only: no receipt waits more than 10 s, none for a payment in the scored window went out later than that, and none is set aside. A setting the worker cannot use stops receipts and is logged, and the worker re-reads its settings while it waits, so `revert_config` works at once. `crash`, `stopped_worker` and `bad_setting` refuse notifications in a copy that does not run it. |
| 2026-10-30 | Contract 1.2: the checker keys and validity rules that issue #4 asked for | Every checker now also returns `integrity.harmful_quarantines` (the items set aside that it does not class as poison; the bank's is `wrongly_quarantined` plus `receipts_set_aside`) and `impact.time_to_mitigate_s` with `impact.mitigation_censored` (from the 5 s buckets in order; a bucket with no journeys keeps the state of the one before it), so `eval/` can score harmful quarantines and time to mitigate without reading system-specific keys. The oracle-red exclusion applies to fixable cases only: a must-escalate case is excluded only if `noop` is green, and `oracle` is not re-run on it, because it skips the escalate fix and stays red by design. The transfer run adds `noop` and `oracle` on 3 copies, so its cases are validated like the exam's within the same hour. The new keys change no verdict, and the default bank is unchanged. |
| 2026-10-30 | Contract 1.2, completed from the review of the overnight pull requests | The safety wrapper writes a `read_error` audit line when a read cannot reach the system, and the harness counts such a case as a harness error for every arm: the AI arms catch the error and hand over, so without the line only the runbook's unreachable cases would be re-run. `act()` documents its optional `reason`, so confirm prompts and audit lines say why. A dev run without `noop` and `oracle` (the pilot, the runbook tuning) skips only those two checks and says so, so the pilot report is not empty. The strata are defined from the labels, with healthy cases counted as single, as the seal's composition counts them. No verdict, label or default bank behaviour changes. |
| 2026-10-30 | Agent tuning on dev-01 to dev-20 with the real model: one fault can hide another | The assessment prompt now says that while a component is down, the components after it get no work and their own faults show no symptom, and that a setting changed to a value that cannot work is a fault before it shows one. In a three-fault practice case the agent dismissed such a setting as a change with no symptom, and it surfaced only after the time for one more reassessment had gone. The same sentence is in the react arm's instructions, so the ablation still differs only in its survey and triage order. |
| 2026-10-30 | Agent tuning: the sustained check stops after two bad looks in a row; a reassessment starts while 26 s plus the handover remain | After a fix that did not work, the check used to take a third look before giving up, and the reassessment needed 30 s plus the handover. Both cost the last reassessment in the same three-fault case. The arm still needs two clean looks in a row to call a recovery. |
| 2026-10-30 | Agent tuning: a page becomes a follow-up once the fix held | After a working failover the model sometimes also escalated the slow primary, and the escalation was a page ("now"), so a recovered system was reported as escalated. Once the sustained check passes, an escalation on components the agent acted on successfully, with no open fault left there, becomes a follow-up ("soon") and the outcome is `recovered`. An escalation on a component the agent could not act on (an outage at another organisation) stays a page. Every AI arm applies it. |
| 2026-10-30 | Agent tuning: work only people can do always reaches a person | Every item the agent quarantines becomes a follow-up escalation naming the item, as CONTRACT section 4 asks for poison messages. A failed data check counts over a trailing window and stays up after its cause is fixed, so from the second look on, a count that has not grown since the look before is past damage: it no longer blocks recovery, and it is handed to the operations team as a follow-up. A count that is still growing keeps the check red. |
| 2026-10-30 | Agent tuning: the handover hears how recovery was checked | The SBAR facts now include the last recovery check, say that the incident commander took the actions itself, and, when nothing was wrong, list the changes the survey saw. The SBAR prompt asks for one or two sentences per part and specific names. Before this, the notes called the agent's own actions automatic and said recovery was unconfirmed when the sustained check had passed. The class meanings for `poison_message` and `stale_cache` follow CONTRACT section 4. |
| 2026-10-30 | GO/NO-GO 1 passed on the morning rehearsal; the 14:30 re-run is dropped | Session A's C4 rehearsal on `main` at `8d21c9e` passed all four steps in BUILD-PLAN section 7 (one-command start, the 6 practice faults break and heal, `check` agrees, three copies cycle without port errors), and the bank has not changed since. Omar counted it as GO/NO-GO 1 at 10:31, so the runbook tuning can start once the scoring and runbook pull requests (#9, #10) are merged, instead of at 16:30. |
| 2026-10-30 | The freeze moves from 21:00 to about 18:00, so the full exam fits overnight | Every incident takes about 2.5 minutes whatever the arm, because the verdict time is fixed from the alert (about 2.4 minutes per case on the real bank in a Linux test this morning). The full run (60 cases × 7 arms plus 220 robustness runs on 3 copies) then needs about 9 hours, which a 21:30 start cannot finish by 06:00, so GO/NO-GO 3 would have cut it to core40. With GO/NO-GO 1 passed, the agent tuned and the runbook tuned this morning, the pilot moves to about 13:00, the dry run to about 15:00 and GO/NO-GO 3 to about 16:00, and the final run starts at about 18:00. GO/NO-GO 3 now asks whether the run ends by 05:30 from its planned start, instead of whether it takes 8 hours or less (BUILD-PLAN section 7). Omar chose this at 10:33. |
| 2026-10-30 | Agent tuning on harder incidents built from practice fault types: crash history from before the agent's own action is not a crash loop | A smoke incident crashed a process three times before the alert. The agent restarted it and the system came back, but the check kept failing on the exit count, because three exits within 30 s read as a crash loop, and the agent handed a recovered system to a person. Exits that all came before the agent's last successful action on that component are now history, in every look and in the reassessment survey. An exit after the action still counts. The action's age comes from the agent's own clock. |
| 2026-10-30 | Agent tuning: a page for a component that recovered once its callers were fixed is dropped | In smoke incidents where the bank's own timeout toward an outside service was set to a value that cannot work (the pattern the build thread found in the runbook), the agent reverted the setting but also paged the outside service's operator, so a recovered system was reported as escalated. After a passing check, a page ("now") is now dropped, with its root-cause claim, when the agent tried no action on the components it names, each of them is called by a component the agent fixed, and the last look shows no fault there. The handover says why. This narrows the earlier row "a page becomes a follow-up once the fix held": a page on a component the agent could not act on stays when it still shows a fault, or when nothing that calls it was fixed. Every AI arm applies it. |
| 2026-10-30 | Agent tuning: the confirming look moves closer when time is short | In a smoke incident with faults arriving during the response, the agent fixed all four, had one clean look, then ran out of budget during the 4 s gap before the second look, and ended `budget_exhausted` on a recovered system. The gap now shrinks so the next look still fits, never below 1 s, with half a second spare for the clock. If even that does not fit, the check stops as before. The arm still needs two clean looks in a row. |
| 2026-10-30 | Agent tuning: when a reassessment finds nothing new to try and the main journey passes, the agent checks again | Before, a reassessment that proposed nothing new ended the response with a page to the on-call engineer, even when the main journey passed and the symptoms were fading. Now the agent runs the sustained check again, if it still fits in the budget and the step cap; otherwise it hands over as before. |
| 2026-10-30 | Agent tuning: a component that is down at a reassessment is brought back | In a smoke incident a process went down again after the agent restarted it. At the reassessment the model read the restart as an action that had failed to help, escalated instead of restarting, and left the service down to the end. The reassessment instructions now say that a component that is down now is brought back with the allowed action most likely to keep it up (another restart if nothing points to a cause an allowed action fixes), followed by an escalation if the reason is still unknown. The guard still allows at most two of the same action on one component. |
| 2026-10-30 | The agent honours the system's access cap and minimum window | From the build thread's check of the guide for adding a system. The incident now runs in the lower of its mode and the profile's `max_mode`, as CONTRACT section 9 says: advise when `act` is false, and with a confirm cap and nobody to confirm, every action is declined, as the runbook does. It never asks observe() for a window shorter than `min_window_s`, and it reads an exit count that comes without the time of the last exit. The bank declares auto, act and a 2 s minimum, so nothing changes there. |
| 2026-10-30 | The scripted runbook also runs in the transfer test on dispatch | Its rules use only component kinds and the public adapter fields, so it needs no change. The transfer test then compares the agent with the simpler baseline on a system neither was tuned on, not only the agent with `noop` and `oracle`. It adds 20 runs on Saturday (about 15 minutes on 3 copies); the result is descriptive (n = 20). Written in before `freeze-1`, so the analysis plan stays unchanged after it. |
| 2026-10-30 | The bulk model for the final run is `anthropic:claude-opus-5-5` | The agent was tuned on it and the pilot's AI arms ran on it, and its cost per incident in the tuning runs fits the budget. Any other model would put an untried model under the frozen agent in the main exam. `swap` stays `anthropic:claude-haiku-5-5`, so `model_swap` still tests a model the agent was not tuned on. Set in `configs/models.json` before `freeze-1`, so it is in the settings hash. |
